# Static reference data

> Adapted from [Beads marketplace-main `STATIC_DATA.md`](https://github.com/gastownhall/beads/blob/4a67d0d0288c1b4ee23e17fc896f47616931ba2d/plugins/beads/skills/beads/resources/STATIC_DATA.md).

Beads is primarily for work with ownership, status, dependencies, and a useful
lifecycle. Avoid turning every glossary term, configuration value, or mostly
static reference entry into an open work issue. Use documentation or an existing
project knowledge system when it provides clearer name-based browsing.

Validated reusable conventions can belong in Beads memory when they are likely
to help future work and do not already exist. Search first, record scope and
evidence, and correct stale knowledge deliberately. Do not use memory as a dump
of all project facts or as a substitute for authoritative specifications.

If a team has a real need for structured reference entities with relationships
and ownership, design that use separately. Keep it separated from active work
where possible and verify the installed CLI's search and query capabilities
before choosing it. This advanced pattern does not authorize a new database,
initialization, or schema change.
