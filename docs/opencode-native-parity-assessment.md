# Native OpenCode architecture assessment

Planning recommendation, 2026-10-17. **Owner gate pending; no implementation or runtime qualification.** This is part of the [full decision packet](claude-code-integration-analysis.md), not a separate workstream. The complete 73-file Claude corpus and its pending dispositions remain in the [inventory](claude-code-integration-inventory.json). Claude supplies desired behavior, not the architecture.

## Recommended owner bundle

**N1 — recommend a native continuity adapter, package-owned discovery, and scope-aware execution.** Add a narrow typed continuity tool through `ctx.tool.transform` for checkpoint, targeted recovery and selective memory operations, backed by the existing Beads CLI and its durable records. This is an adapter, not a second database or a replacement for all CLI commands. The model supplies meaning, evidence, scope and task/memory selection; the adapter validates the request, checks authority, executes argument-safe CLI operations, reports actual success/failure and marks relevant context stale. Use native context/tool hooks to make recovery and checkpoint opportunities reachable. Keep ordinary CLI workflows available. Pair D01 package commands with D04 a distinctly named supplemental skill and real packaged resource paths. Preserve the upstream-owned shared skill and user customizations. Adopt the full behavioral ambition; deferred corpus entries remain explicit owner choices, never silently disappear.

Recommend **2.0.32 as the qualification and eventual minimum-host target** for N1 because it exposes `ctx.permission.assert` for plugin-owned tool execution. This is a proposed consequential compatibility decision, not a peer-dependency edit or a claim that every mechanism requires 2.0.32. Published 2.0.26 declarations already contain the context, prompt, compaction, tool hooks, command/skill registrations and synthetic interfaces. Permission evaluation hooks also exist there, but the plugin assertion method does not. If retaining 2.0.26 is essential, choose **N0**, using those hooks plus model-issued, normally permissioned CLI operations; do not emulate authorization by silently executing CLI inside a hook. N0 loses the typed persistence acknowledgement/freshness signal and needs stronger behavioral qualification. It is a deliberate compatibility fallback, not the old bounded-worker policy.

**N2 — optional extensions, separately selected:** host-native background subagent completion for authorized long work; nested delegation only when requested scope benefits; an explicitly requested checkpoint-before-manual-compaction workflow. Do not auto-resume after user stop, permission wait or failure. Do not mandate delegation by command count. Bounded one-bead workers and Luna remain optional E01/E02 policies, not the base architecture. Native asynchronous completion can improve responsiveness, but still returns model-authored text rather than a certified semantic handoff.

Matt should decide the consequential bundle (N1 vs N0), full-corpus grouped dispositions, continuation policy and N2/experimental adoption. Engineering owns the low-level mechanism mapping below unless qualification changes a consequential promise. Approval must identify the reviewed revision; nothing here records consent.

## Lifecycle and alternatives

N1 should write synchronously in the typed operation and return a persistence acknowledgement before ordinary continuation; do not create a deferred batching queue just to make a compaction flush useful. Usually the compaction hook only carries acknowledged references and flags gaps. Its awaited seam can finish a genuinely pending, already-authorized operation, but cannot manufacture missing semantic judgment. For N2 manual checkpoint-then-compact, sequence compaction admission only after checkpoint acknowledgement; `session.prompt` and `session.compact` return admissions, not proof that the checkpoint/summary completed.

Permission assertions need a concrete compatibility contract: a new custom action that defaults to allow does not inherit existing shell/worker restrictions. Recommend asserting the applicable existing shell action/resource for the fixed CLI operation and enforcing the relevant task/location/guard restrictions, with argument-safe process execution. Directory/resource policy equivalence must be checked against the built-in shell path (S18); `permission.assert` alone does not reproduce its scanner. If equivalent denial/ask behavior cannot be demonstrated, use N0's normal tool path or return the proposed permission-surface change to the owner. Never silently widen worker authority. This is a material qualification item, not an assertion that native registration is sandboxing.

Load registers package-owned surfaces and bounded, location-scoped hooks, then subscribes to notifications with explicit cleanup. First eligible request resolves actual session scope and authority, provides guarded workflow and targeted recovery. During work, the model selects task checkpoints or reusable-memory operations; the typed tool validates and asserts permission, runs supported CLI arguments and returns an honest acknowledgement. Relevant context becomes stale only on known changes, with targeted reads for external uncertainty. Tool hooks provide focused cues and child-result feedback, not autonomous semantic writes. Compaction waits for any prepared authorized checkpoint operation before summarization; it does not request another same-session turn. Completion/failure events update diagnostics without forcing continuation. Reload/deletion abort observers and clear ephemeral state; later recovery reads durable records.

Compared with Claude hook shell scripts, typed tool identity and success/error payloads allow precise feedback without parsing arbitrary shell text; mutable context hooks can scope guidance to the actual session/request; native inbox/child results avoid a separate completion poller; package registrations can remove discovery entries with package lifecycle. These are evidenced integration affordances, not proof of better model judgment or durability than Claude. Claude's richer resource guidance remains valuable.

CLI-based N0 with native hooks has lower implementation/compatibility cost but weaker acknowledgement and refresh precision. Blanket automatic extraction from tool output is rejected because transport success does not establish reusable meaning and introduces privacy/duplication errors. An end-event-triggered “save everything” loop is rejected because it races shutdown/compaction, can undo deliberate stop and recursively trigger itself. Custom compaction replacement or auxiliary `generate` could extract semantics, but adds model cost/failure/authorization and provider-state consequences; it is not the recommended base. Keep a seam for a later, explicitly selected extractor if evaluations show periodic typed checkpoints insufficient.

## Qualification and owner gate

Executed evidence is source/API/package inspection and static consistency validation only. No inference, server startup, dependencies installed, product tests, bd commands or store operations. Type presence is deterministic; actual checkpoint quality and appropriate remember selection remain model-dependent.

After owner selection, only material unknowns need controlled probes: installed N1 tool permission allow/ask/deny and cancellation; direct versus code-mode duplicate acknowledgement; collision/disposal/resource resolution; same-session synthetic queue/wake/reentrancy under stop and permission wait; native/summary compaction ordering with a slow or failed prepared write; blocking/background child return and NO_TEXT. Use disposable fixtures and stub CLI first. Host execution or model inference needs separate authorization. Retaining 2.0.26 requires its own focused call-site/runtime checks where source differs; type equality alone is insufficient. Behavioral scenarios remain those in the full packet, adding continuous-session freshness and failed precompaction persistence. No exhaustive model matrix.

N1 acceptance chooses the proposed minimum and ownership bundle, not experimental flags. Record X01–X09 dispositions and N2 continuation choices explicitly. If a selected guarantee cannot be met, report the degraded behavior and return only consequential changes to Matt. Keep all F/D/E and corpus dispositions pending until approval. The removed freeze marker and parent-reconciled tracker are not defects or research prerequisites; no current store hold is asserted by this assessment.
