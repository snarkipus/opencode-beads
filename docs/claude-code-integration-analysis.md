# Full Beads integration experience: analysis and owner decision packet

Status: planning evidence collected on 2026-10-17; **owner decision pending; product implementation blocked**. This document recommends behavior and delivery choices. It does not establish full parity, approve any feature, or authorize store access. The historical [lifecycle comparison](claude-code-parity.md) remains evidence for its narrower target.

## Outcome and evidence boundaries

Matt reports better ongoing task notes and more appropriate `bd remember` use with Claude Code's Beads integration than with OpenCode and OpenAI models. This is an observed user experience, not controlled evidence that the host, provider, model, or prompt caused it. The objective is recovery of attempted approaches, learning, rationale, blockers, and the next action across sessions without repeated user prompting. More writes alone are not success.

This review enumerates the full shipped plugin subtree, shared skill template, marketplace entry, and the implementation paths that connect them. Static source evidence establishes availability and intended wiring, not that a model loaded a resource, followed a prompt, or successfully invoked a stale command. No Claude/OpenCode inference trial or Beads command was run. Examples of Beads commands below describe future behavior only.

The [native architecture assessment](opencode-native-parity-assessment.md) completes the behavior-to-mechanism investigation: released V2 call sites, experimental candidates, preferred N1 bundle, 2.0.26 fallback N0 and explicit qualification gaps. It refines the delivery recommendation below without replacing the complete Claude corpus or accepting any pending disposition.

## Guidance, memory and conflict analysis

The rich skill/resources provide substantially more advice about *when* to write and *what meaning to preserve* than the lean shared skill. `WORKFLOWS`, `PATTERNS`, `RESUMABILITY` and `INTEGRATION_PATTERNS` cover milestones, current state, key decisions, tested examples, blockers and next steps. They also conflict: some recommend ephemeral TodoWrite while current prime prohibits it; WORKFLOWS asks permission at every handoff and tells agents to overwrite notes, while other passages advocate proactive updates. The skill says initialization is human work yet its error table suggests initialization as the fix. Stale version strings and MCP examples coexist with the ADR's canonical-prime principle. These are reasons to adapt, not evidence that all upstream behavior is desirable.

Recommended base behavior is to checkpoint meaningful transitions: a failed approach with why it failed; a validated discovery; a changed decision; a blocker; delegation return; stopping/compaction when feasible. Save enough of the previous rationale to avoid repeating dead ends. Current-state notes can summarize the active position; comments can retain useful chronology. Issue descriptions/design/acceptance have distinct roles. Ordinary authorized task updates should not need repeated user prompting, but an explicit hold or missing authority still wins. An abrupt process loss cannot guarantee a final write, so periodic meaningful checkpoints matter more than relying on an end hook.

Reusable memory needs a separate decision: is the finding supported, project-relevant, likely useful beyond this issue, and absent or outdated in existing memory? If so, preserve its evidence/context and applicability, using the supported memory CLI. A temporary failure is usually a task note, not universal knowledge. On recovery, read the active issue and relevant memories before choosing the next action; prime is a workflow/memory entry point, not a complete reconstruction of all issue notes. No fixed write counts, token targets, or automatic memory dump are proposed.

[Local guidance](../src/guidance.ts) currently requires delegation for multi-command work/graph analysis and allows only single atomic operations in the primary. The worker prompt says one bead, create discoveries but never work them in that invocation, validate, close/block, return concisely. It does not explicitly require returning failed attempts, learning, or memory keys. A concise return can lose precisely what the primary needs to preserve. Recommended handoff includes task state, attempted approach/outcome, evidence, rationale, blockers, next action and durable record references when relevant. The primary should reconcile the result before closure or continuation. Whether all multi-command work must delegate is an owner decision: preserve direct atomic operations and graph analysis as distinct scenarios, without treating command count as a universal reason to surrender context.

[Context](../src/context.ts) caches by session **and audience**, coalesces loads within that key, retries absence/failure after 30 seconds, and refreshes after compaction or a 30-minute idle gap by default. Every request gets cached text. Continuous activity can retain old memory indefinitely; idle refresh is not an exact resume event. Independent child sessions and different audiences may prime separately. [Host](../src/host.ts) invalidates on `session.compaction.ended`, forgets deleted sessions, and adds summarization guidance for IDs/status/follow-ups/blockers/validation. It does not persist semantic progress itself. Targeted fresh reads at recovery or after relevant changes are a simpler candidate than re-running full prime every model step or adding a new memory service.

[Guard](../src/guard.ts) checks version/location/marker before automatic prime, but it is not a sandbox for subsequent model shell calls. The migration notice says not to run bd; static skill/worker/failure fallback says run prime when context is missing. Future guidance must distinguish **withheld** from **failed** context so manual recovery cannot bypass a hold. `autoMigrate` and permission rules are existing options, not authority to change this repository now. [Instruction minimization](../src/instructions.ts) strips matching full/Codex managed blocks in requests when prime is attached; it does not prove those blocks are semantically redundant (profiles and updated policy can differ). Retain local authority and test non-duplicate constraints before extending minimization.

### Local tests: what is and is not established

`tests/context.test.ts` checks mocked cache, audience, retry, idle and invalidation behavior. `tests/host.test.ts` checks hook registration, flags, guard wiring, compaction guidance and cleanup. `tests/guard.test.ts` verifies the limited safe probe sequence and notices. `tests/instructions.test.ts` checks marker transformation and preservation outside blocks. `tests/guidance.test.ts` asserts prompt strings and a prompt length ceiling; it does not show model comprehension or durable note quality. `tests/agents.test.ts` exercises a copied permission matcher, not a complete host sandbox; source explicitly acknowledges wrapper/alias bypass. Historical live observations apply to their recorded 2.0.26 scenarios only. None of these establish fresh-session recall, appropriate remember selection, or full marketplace experience parity. No product tests were run for this planning-only change.

## Native delivery choices and extension model

The [V2 command documentation](https://opencode.ai/v2/docs/commands/) explicitly supports Markdown templates and JSON commands; see its [pinned source](https://github.com/anomalyco/opencode/blob/8f7b0120eb6b4aa3da1f82b1a9094a9fb4db2d06/services/www/src/docs/content/commands.mdx). The [plugin API](https://github.com/anomalyco/opencode/blob/8f7b0120eb6b4aa3da1f82b1a9094a9fb4db2d06/services/www/src/docs/content/build/plugins/index.mdx) separately registers executable commands. The old artifact-policy wording confused these surfaces. Native prompt commands are a viable option; removal of vendoring was a policy choice, not a platform necessity.

| Owner choice | Benefits | Ownership/removal/override and risk |
| --- | --- | --- |
| D01: package-owned executable commands | One package/version controls registration and removal; no project-file installer | Must forward prompt attachments/delivery correctly, define naming/collision behavior, and verify user override precedence at the supported host. More adapter code; never directly interpolate user arguments into shell execution. |
| D02: explicit project/global Markdown command install | Native editable prompts, description and argument substitution; familiar file review | Needs an explicit installation/update/removal contract and provenance. Preserve user edits/collisions; remove only owned unchanged files. Project commands override global ones. Avoid shell-output interpolation: V2 evaluates it outside agent tool permission flow. |
| D03: JSON command configuration | Native templates and agent/model selection | User config merging/removal is harder to own safely; no unrequested runtime-config edits. Keep as documented alternative rather than automatic mutation unless selected. |
| D04: package-owned skill registered with real asset path | Resource base can be packaged and versioned; uninstall follows package registration | Npm internals are not automatically discovered. Must provide a valid path and package resources, test resolution after install, and establish user override behavior. |
| D05: supplemental skill in native discovery directories | Explicit resource tree and user-controlled customization | Shared `beads` ID collisions can shadow content. Prefer a distinct supplemental ID unless Matt intentionally selects a replacement; duplicate discovery prompts may confuse models. Upgrades/removal need ownership discipline. |
| D06: lean shared skill plus runtime guidance only | Minimal asset/installer maintenance | Can add checkpoint/recovery triggers but lacks the rich progressive resource experience unless references are actually reachable. Must demonstrate outcome and discoverability rather than assume prime alone suffices. |

Revised recommendation: **N1 with D01+D04** is the preferred bundle: typed continuity operations, awaited context/tool/compaction hooks, observational events, package-owned executable commands and a distinct supplemental skill with real resource paths. Instructions/resources supply semantic judgment rather than being the sole integration mechanism.
